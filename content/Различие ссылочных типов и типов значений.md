Переменная типа значения содержит экземпляр типа. Переменная ссылочного типа содержит ссылку на него.

> [!important]  
> Переменная значимого типа может иметь поле ссылочного типа  

Нельзя унаследоваться от значимого типа.

У экземпляра значимого типа нет индекса блока синхронизации (для Monitor и lock).

По умолчанию в C# аргументы передаются в метод по значению. Для типа значения копируется сам экземпляр, для ссылочного типа копируется ссылка на объект. Поэтому метод может изменить поля переданного объекта, и вызывающий код это увидит. Но если метод присвоит параметру новый объект, переменная в вызывающем коде не изменится. Передать саму переменную по ссылке можно модификаторами `ref`, `out` и `in`.

```csharp
void Change(List<int> list) { list.Add(1); list = new List<int>(); }

var items = new List<int>();
Change(items); // в items теперь 1, но это всё тот же старый список
```

Имеет **смысл использовать значимые типы**, когда:

- тип ведет себя подобно примитивному, у него нет членов, которые изменяют его экземплярные поля (тип неизменяемый, immutable).
- У типа нет другого базового типа
- У типа нет производных типов
- Экземпляр маленький (или, если большой, не передается как параметр метода или не возвращается из метода)

**Упаковка** - преобразование значимого типа в ссылочный.

- Выделяется память в куче под тип и указатель на типовой объект и индекс блока синхронизации
- Поля значимого типа копируются в память в кучу
- Возвращается адрес - ссылка на объект

При распаковке должно быть приведение к точному типу, каст типа int32 вместо int16 не допускается.

Приведение неупакованного экземпляра значимого типа к интерфейсу требует, чтобы экземпляр был упакован, т.к. интерфейсные переменные должны содержать ссылку на объект в куче (нормальным языком, интерфейсы имеют ссылочный тип).

### Зачем IL нужен стек (Эрик Липперт)

Речь о **стеке вычислений** языка IL (MSIL/CIL), а не о стеке потока, где лежат локальные переменные и значимые типы.

Компилятор C# переводит код не сразу в машинные команды, а в промежуточный язык IL. Во время работы JIT-компилятор превращает IL в машинный код конкретного процессора. Так дешевле: на 20 языков и 10 процессоров нужно 20 + 10 = 30 генераторов кода вместо 20 × 10 = 200.

IL устроен как стековая машина, потому что это простая модель: под неё легко писать и компиляторы языков, и JIT-компиляторы. К тому же промежуточные результаты вычислений нужны совсем недолго: получили, использовали, выбросили. Ровно это и умеет стек.

Если бы IL работал только с памятью, выражение `x = A() + B() + C()` выглядело бы так:

```
Allocate temporary store T1 for result of A()
Call A() with the address of T1
Allocate temporary store T2 for result of B()
Call B() with the address of T2
Allocate temporary store T3 for the result of the first addition
Add contents of T1 to T2, then store the result into the address of T3
Allocate temporary store T4 for the result of C()
Call C() with the address of T4
Allocate temporary store T5 for result of the second addition
...
```

Код разрастается: под каждый промежуточный результат приходится явно выделять память, а каждой команде передавать адреса операндов и адрес для результата.

Тот же код на стеке:

```
push [address of x]
call A()   // результат A() кладётся на стек: временная память появляется сама
call B()
add        // снимает два значения со стека и кладёт сумму
call C()
add
store      // сохраняет значение с вершины стека по адресу под ним, то есть в x
```

Код стал короче и проще, а команды компактнее: `add`, который берёт два значения со стека и кладёт одно, занимает один байт. Такой компилятор легче писать, поддерживать и анализировать. При компиляции в машинный код JIT раскладывает значения стека вычислений по регистрам процессора.
